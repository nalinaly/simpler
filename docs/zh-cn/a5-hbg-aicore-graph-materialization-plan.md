# A5 Graph 物化优化方案：先并行构造，再评估分阶段发布

**修订日期**：2026-11-02。**实现起点**：`f0722c567`。
**状态**：范围规划器、私有工作项布局及 CPU 缓存模型测试已实现；
尚未接入实际 bootstrap，多核设备构造、A5 缓存一致性和性能验收仍未完成。
本文承接[总设计](a5-hbg-aicore-graph-design.md)的 P5，
事实依据见[物化提案复核](investigations/2026-11-a5-graph-materialization-review.md)。
首版已有的功能测试和性能数据不能作为本方案的验收结果。

范围规划器对实际引用做区间合并与去重，按物理写回单元分组；
9 个 CPU 用例检查共享槽位、空洞、未对齐 Scalar、越界和跨区域重叠。
延迟整行写回模型在 32 种完成顺序下保留全部已引用 Scalar，
其按元素分配 writer 的反例会丢失更新；这不是 A5 真机可见性验收。

## 1. 目标、顺序与保留的行为

现有实现按实例分配物化 owner。单个大实例仍由一个核构造，
全部实例物化完成后才进入 ready bootstrap；这使首任务等待包括整个 run 的构造时间。

后续顺序固定为：

| 阶段 | 主要改动 | 执行放行条件 |
| ---- | -------- | ------------ |
| P5a：并行构造 | 大实例按可写范围分块，多核构造；小图合并工作项 | 保留所有实例成功物化后才执行的启动屏障 |
| P5b：分阶段发布 | 完整验证与数据生成分离，再评估按实例生成/发布 | 先完成全 run 的可失败验证；发布实例的数据对所有消费者可见后，才满足它的物化条件 |

P5a 首先改善大单图的构造并行度，不宣称已实现构造与执行重叠。
P5b 首先研究多实例重叠；单实例的分片发布还需要独立的依赖和发布进度协议。
消费端逐行失效是 P5b 的候选配套，不与 P5a 同时更换。

两个阶段都保留以下行为：

- Graph API、Definition 编码、公共父子身份和原有合法输入范围不变。
- 原本在启动物化阶段能发现的错误，必须仍在任何 kernel 进入前报告；
  包含健康实例的输出保持原值、正确 first error、poison 与存储退休行为。
  这不是对执行中任意 kernel 故障提供回滚。
- child 就绪仍受 ENTER/内部 fanin 控制；实例物化成功不等于外部依赖已经满足。
- 构造工作不调用 kernel、不等待外部 fanin；正常执行核资格、公平竞争和协同准入不变。
- 无 Graph run 不增加 Graph 分配、扫描和消费端缓存操作。
- 保留 `remaining_children`；只有测得完成聚合争用后才另行研究分片计数。
  新增构造工作项的完成计数不能代替 child 完成计数。

本方案不新增用户环境开关或公共执行模式。工作量和运行核数决定内部工作划分，
小图与大图使用相同的有效性和发布保证。

## 2. P5a：保留启动屏障的并行物化

### 2.1 拆分验证职责与构造职责

先将现有 `scheduler_graph_materialize()` 的检查项逐一列入对应 helper 的合同，
保留其错误类型及父/子身份：Definition framing、实例/epoch、地址与大小、
子任务字段、Tensor 重绑、Scalar 继承、predicate 和存储布局。

验证负责证明读取和写入的合法性；构造负责生成指定输出范围。
职责拆分不要求每轮无条件全量遍历两次：P5a 可以在独占范围内边检查边写入，
因为所有构造完成前执行 gate 始终关闭。不能把检查删掉后称为“纯构造”。
Host 已对共享 Definition 完成的结构检查不应被每个 chunk 完整重做；
实例地址、epoch 和该工作项涉及的运行时绑定仍需验证。

### 2.2 按物理写回范围分配唯一写者

工作项只属于 bootstrap 构造阶段，不增加公共 TaskId、Graph child 或 ready task。
其计划至少能定位实例、区域种类、元素/字节范围和错误对应的公共身份。

| 区域 | 划分要求 |
| ---- | -------- |
| descriptor / payload | 按完整任务存储记录划分，并保证相邻 chunk 的缓存写回范围不交叠 |
| Tensor pool | 按描述符存储范围划分；同一个参数池槽位只构造一次 |
| Scalar pool | 按完整写回单元分组；不能把同一缓存行内的不同 Scalar 交给不同 writer |
| 控制和发布字 | 与数据写回隔离，沿用对应原子/bypass 发布原语 |

唯一写者针对**可能写回的整条缓存行**，不只是 C++ 字段或 child 编号。
必须检查区域交界、尾部不足一行的部分，以及不同实例是否共用写回单元。
不能用结构的 `alignas(128)` 推导 DCache 操作粒度。

参数区间可能共享槽位、存在空洞或在边界上相邻；计划须从实际合法引用建立覆盖，
不能假定一个 child 就拥有一段互不重叠的参数池。
共享槽位归并给一个 writer；未引用的内容不因新遍历方式变成新增拒绝条件。
一条物理行内存在多个写入区间时，由同一工作项或同一 owner 处理。
无法证明隔离的范围合并为串行工作，而不是允许多个核重复写“相同值”。
不同实例之间仍必须证明写回范围隔离；如果需要布局 padding，
须显式计入 checked sizing 和分配预算，不能仅串行化各实例内部就认为问题消失。

不要求固定某个物化核。小图合并工作项，避免领取与计数开销超过构造成本；
大图的粒度依据运行核数、实际记录数和参数字节数规划。
粒度阈值由后续实测确定并记录，不能先写成收益承诺。

### 2.3 领取、完成与唯一发布

沿用 run-owned 调度存储和现有原子原语，构造过程如下：

1. 初始化本轮计划、实例状态和剩余构造项数；发布不可变计划后才允许领取。
2. worker 原子领取唯一工作项；检查 epoch、运行错误状态和工作范围，再构造数据。
3. writer 完整写回自己负责的范围并执行 barrier，之后才能贡献一次构造完成。
4. 实例的最后一个成功贡献者取得唯一发布权。只有全部构造项成功、
   实例未失败且本轮没有阻止启动的错误，才能发布该实例物化成功并贡献 run 级完成。
5. 最后一个成功实例沿原有隔离信号发布 run 完成。
   等待方继续使用成功信号与原子零值确认，并保留消费核的启动缓存观察，
   随后进入原 ready bootstrap 和 kernel 放行过程。

这里的“最后一个贡献者”是发布 owner，不再要求它构造整个实例。
构造项只能贡献一次；不能因重试、重复领取或重复完成使计数提前到零。
实例失败状态是终态，成功贡献者不得覆盖它；完成数相等不替代状态、epoch 和错误检查。

任一构造项失败仍报告现有 first error，保留合法父/子身份。
停止新领取、让已领取工作有界退出，按照现有退出握手证明所有 writer 静止后再回收。
错误退出不能要求成功计数归零，也不能因启动未成功就提前释放写者仍可能访问的区间。
超时预算覆盖整个启动阶段，不因每领取一个 chunk 而重新开始计时。

### 2.4 存储与开销预算

设实例数为 I、工作项数为 C、去重后的区间描述数为 U，
新增控制与计划规模应为 `O(I + C + U)`；共享 Definition 的区间计划优先按定义复用。
不分配每核一份完整 Graph，也不复制子任务存储或整个参数池。

预算必须分别列出工作项、区间映射、构造计数、对齐填充、trace 和 retained 高水位。
不要先假定它们能放进旧结构的 padding；实际布局以 `sizeof/alignof` 和 checked sizing 为准。
空参数区域不生成空工作项，合法的无 Graph run 新增字节数和新增扫描数都必须为零。

领取/完成 RMW、计划生成、重复校验、写回和等待均计入成本。
P5a 保留原启动消费端缓存维护，不把改为逐行失效带来的变化混进并行构造的收益。

### 2.5 并行构造的协议证据

P5a 就需要同步 Graph 协议记录与审计，不能把多核构造伪装成发布 owner 独自物化。
诊断模式须能对应冻结的范围计划，证明领取唯一、范围完整、写回早于完成贡献、
全部成功贡献早于实例发布，以及所有实例发布早于 kernel 放行。
构造贡献与 child 终态贡献分开计数；现有 `graph_contribution` 的完成语义不混用。
记录布局变化时显式演进 schema 并保留旧捕获解释，L0 不增加逐项 trace 写入。

## 3. P5b：验证先完成，再评估延后生成与发布

### 3.1 进入条件与失败边界

仅在 P5a 正确性通过、测量仍显示值得处理的启动等待后进入 P5b。
首先把原本由物化发现的所有错误移到执行 gate 打开前的完整验证阶段，
并冻结本轮 Definition、参数元数据、实例地址和构造计划的只读视图。
实际 Tensor 数据继续按 DAG 正常读写，不属于冻结对象。

验证位置优先复用已有 Host 结构检查和设备启动检查。
不得把原有设备错误身份、fresh backend publication、poison 或退休行为
悄悄改成 Host fallback，也不能以“之后不太可能出错”省略可失败检查。

只有证明延后生成是对已验证、不变输入的有界写入，
不会新增原本应在启动时发现的错误，才能允许健康实例先执行。
若完整前置验证仍需全 run 屏障，应明确保留并计入成本；
P5b 不承诺消除所有启动屏障，也不承诺额外验证遍历一定更便宜。

第一种候选是外部依赖满足后按实例生成、发布，再由 ENTER 释放 roots。
单实例仍需全体构造完成，因此这不等于单实例分片执行。
后者需要单独设计已发布前缀、依赖注册和恰好一次发布，不能隐含在本阶段名称里。

### 3.2 完整的消费端可见性

若评估用逐行操作替代物化后的全 DCache 观察，必须覆盖：

| 消费者 | 最早读取与要求 |
| ------ | -------------- |
| 普通调度路径 | 在 payload parser 读取计数和相对地址之前建立可见性 |
| MIX 调度路径 | `scheduler_dispatch_mix_ready` 会在 prepare 前解析，维护必须早于该解析 |
| Scalar 参数组装 | 读取的是独立 Scalar pool，不能只刷新 child storage |
| 实际 kernel 执行核 | Tensor 参数是描述符地址；每个参与执行的核都需要相应读取保证 |
| predicate 与其他启动数据 | 保留 predicate 元数据/operand、callable 表及其他原有启动读取的保证 |

producer 的写回与 barrier 必须先于发布；消费者观察正确 epoch 的发布后，
在最早读取之前完成必要维护。维护范围不能覆盖另一个尚在写入的工作项，
也不能把刷新物化核当作刷新其他核。
逐行操作的次数、重复维护和目标核开销都计入端到端对照。

### 3.3 进度与诊断

延后构造不能依赖已经被阻塞 kernel 占住的核才有机会继续执行。
必须验证 ordinary、MIX、sync_start 和跨实例依赖下的服务进度，
并覆盖[已有 Graph/drain 反例](../investigations/2026-09-hbg-graph-release-vs-drain-reorder.md)。
长 ENTER 的服务时间要有界；唯一 ready owner 只证明排他性，不证明进度。

协议记录区分验证、构造项、实例发布、ENTER、child 完成和 EXIT。
更新严格审计规则，使其证明新时序，而不是删掉旧屏障断言后只检查最终数值。
如果 wire 或 trace 字段改变，要显式演进版本并保留旧捕获的解释。
L0 不增加逐构造项 trace 写入；诊断采集和性能采样分开。

## 4. 实施落点与验收

### 4.1 实施顺序

| 顺序 | 主要落点 | 完成条件 |
| ---- | -------- | -------- |
| 固定现状与拆分职责 | `scheduler_graph_materialize.h`、现有 Graph UT/故障场景 | 校验清单、合法输入及错误行为不变；保留可比较的串行基线 |
| 构造范围规划 | Host `scheduler_graph_binding.h`、Graph 私有布局 | 覆盖、唯一写者、共享槽位、尾部、溢出和预算检查通过 |
| 多核构造与发布 | `aicore_executor.cpp`、Graph 状态及缓存原语 | CPU 交错模型、CCEC 构建、A5sim 和 A5 功能/故障验证通过 |
| P5a 性能验收 | 既有 benchmark、STRACE 和协议采集工具 | 保持原负载与数值，得到首任务及完整 RunWall 的受控 A/B |
| P5b 条件研究 | 完整前置验证、普通/MIX parser、执行核可见性、协议审计 | 先证明失败边界和进度，再实现候选并单独测量 |

`remaining_children` 的分片归约不在上述改动中。
只有后续测得完成聚合是独立瓶颈，才增加对应设计与对照。

### 4.2 正反例

- 对照串行基线逐字段检查 descriptor、重绑 Tensor、Scalar 和 predicate。
  不能用仅比较最终 kernel 输出替代构造数据和身份检查。
- 覆盖每个应写字节、唯一物理行 writer、共享参数槽位、空参数池、未引用区间、
  不足一行的 Scalar 尾部、相邻实例，以及跨范围边界。
- 人为暂停 writer、乱序完成、重复完成、旧 epoch、最后成功贡献与失败竞争；
  缺一块、未写回或失败时，不得发布成功或打开 kernel gate。
- 保留健康实例与失败实例混排时零 kernel 进入、输出不变、正确 first error、
  poison、在途存储不能提前释放及退出后恢复的现有验收。
- 在原有支持范围内覆盖 AIC/AIV/MIX、predicate、sync_start、跨实例依赖，
  以及重复 replay 时地址、Scalar、图大小和参数大小变化。
- CPU 模型检查调度和发布顺序；模拟非一致缓存的测试及 A5 真机验证负责写回可见性。
  普通 CPU stub 上的成功不能替代后两项。

### 4.3 性能与资源门槛

测量从合法小图到大单图（包含 1024 child）及容量允许的多实例场景。
区分 task 数、参数字节数和实例数，避免把三者一起改变后误判原因。

主要指标为设备启动到首个真实 kernel 的延迟与完整 Device RunWall。
另报验证、构造、写回/发布、等待、Host bind、Host 总调用及新增 GM/retained 字节。
跨核时间必须处于已校准的同一时钟域；不能直接相加各阶段独立分位数。

固定同一 native 基线的编排、Definition、输入、kernel 二进制、原 N、线程配置和 golden，
仅改变被评估的物化方案。native/legacy 对照只作完整后端参考，不用于归因。
每组记录源码提交及未提交 runtime 差异、实际 native/runtime 二进制摘要和工具链版本，
确认执行的构建来自对应源码，不能以分支名代替构建身份。
按设备队列与架构预检规则运行，交替 A/B 并插入同二进制重复对照；
首调用单列，稳定态保留全部样本，同时报告批次差异、中位数和尾部。

P5a 纳入主线的条件是：大单图首任务延迟得到可重复改善，完整 RunWall 没有稳定回退；
小图、多实例和固定无 Graph 负载没有超过同二进制波动的稳定回退。
计划、领取和计数成本必须纳入，不能只报告物化函数局部时间。
差异无法与噪声区分时结论为“不确定”，不能宣称收益或隐藏失败批次。
P5b 单独适用同样门槛，并额外通过失败语义、缓存与进度验收。

实际样本数、批次、粒度阈值与判定方法在取数前冻结并记录。
本方案不预填加速比例；已有 64 个 CPU 用例通过的复核记录不代表本优化已经完成。
